# Domain 1: Output Evaluation and Validation

**Domain Weight:** 21% of CCAO-F Exam
**Focus:** Understanding how to define, measure, validate, and ensure the quality, safety, and reliability of AI-generated outputs across various domains and risk profiles.

---

## 1. What Makes a High-Quality AI Output

Evaluating AI output requires moving beyond subjective feelings of "good" or "bad" into measurable criteria. A high-quality output is one that fulfills the user's intent while adhering to strict standards of correctness and safety.

### The 4 Core Quality Dimensions
1. **Accuracy (Factual Correctness):** The output contains information that is factually true and supported by evidence or the provided context.
   * *Passing:* Stating the current CEO of Apple is Tim Cook.
   * *Failing:* Claiming Steve Jobs is the current CEO of Apple (factual error) or claiming Tim Cook was born in 1990 (hallucination).
2. **Completeness:** The output addresses all parts of the prompt without omitting crucial information, while avoiding irrelevant fluff.
   * *Passing:* Answering a 3-part prompt with a structured response covering all 3 parts.
   * *Failing:* Answering only the first part of the prompt and ignoring the rest.
3. **Tone (Persona and Style):** The output matches the desired voice, whether professional, empathetic, authoritative, or casual.
   * *Passing:* A customer service bot apologizing professionally for a delay.
   * *Failing:* A customer service bot using slang or emojis when addressing a serious billing issue.
4. **Format (Structure and Syntax):** The output adheres strictly to structural constraints (e.g., JSON, markdown, specific word count).
   * *Passing:* Returning a valid JSON object with the exact keys requested.
   * *Failing:* Returning a valid JSON object wrapped in markdown code blocks when the prompt explicitly forbade markdown, breaking automated parsers.

### How to Write a Quality Rubric
A rubric must be specific, observable, and measurable. Avoid vague terms like "good."
* **Bad Criterion:** "Is the tone appropriate?"
* **Good Criterion:** "Does the output use third-person perspective, avoid contractions, and refrain from emotional language?"
* **Structure:** Define a 1-5 scale for each dimension, where 1 is total failure and 5 is perfect adherence. Provide explicit examples for a score of 1, 3, and 5.

### Output Quality vs. Output Correctness
* **Correctness** is objective and binary (or near-binary). Is the math right? Is the code compiling? Is the date accurate?
* **Quality** is subjective and multi-dimensional. An output can be 100% correct but low quality if it is poorly formatted, overly verbose, or uses an inappropriate tone.

### Domain-Specific Quality Expectations
* **Legal:** Zero tolerance for hallucination. Exact citations required. Must not constitute legal advice unless generated by a licensed attorney.
* **Medical:** Precision in symptoms and dosages. Mandatory disclaimers. Must not provide definitive diagnoses without qualifiers.
* **Financial:** Absolute numerical precision. Must use standard regulatory language (e.g., forward-looking statement disclosures).
* **Marketing:** Engagement, brand voice alignment, creativity, and persuasion are prioritized. Factual constraints exist but allow for stylistic flair.
* **Technical:** Code correctness, syntax validity, handling of edge cases, and algorithmic efficiency.

## 2. Hallucinations — Deep Dive

Hallucinations occur when an AI model generates information that is factually incorrect, nonsensical, or unsupported by its training data or provided context.

### Definition and Types
1. **Intrinsic Hallucination:** The model generates output that directly contradicts the provided source text.
   * *Source:* "The meeting is at 3 PM."
   * *Output:* "The meeting is scheduled for 4 PM."
2. **Extrinsic Hallucination:** The model generates output that is not supported by the source text, though it might not directly contradict it.
   * *Source:* "The company's revenue grew by 10%."
   * *Output:* "The company's revenue grew by 10% due to successful marketing campaigns." (Marketing campaigns were never mentioned).
3. **Open-Domain Hallucination:** The model invents facts when answering general knowledge questions without a provided source text (e.g., inventing a historical event).

### Root Causes
* **Training Data Gaps:** The model lacks information on the topic but attempts to answer anyway.
* **Distributional Shift:** The prompt context is wildly different from the model's training data.
* **Over-confident Generation:** The model's objective function favors generating plausible-sounding text over factual accuracy.
* **Prompt Ambiguity:** Vague instructions force the model to guess intent.
* **Helpfulness Bias:** RLHF (Reinforcement Learning from Human Feedback) often trains models to be "helpful," leading them to invent answers rather than admitting ignorance.

### Detection Signals
* Suspiciously specific but unverifiable statistics (e.g., "47.3% of left-handed people...").
* Citations to non-existent academic papers, URLs, or legal precedents (often featuring plausible but mixed-up author names or case names).
* Internal contradictions within the same response (e.g., stating a person died in 1990 in paragraph 1, and quoting them in 1995 in paragraph 3).
* Confident assertions about post-cutoff events.
* Implausible proper nouns.

### Mitigation Hierarchy
1. **Grounding:** The most effective technique. Provide reference text and strictly instruct the model to cite only it.
2. **Chain-of-Thought (CoT) Reasoning:** Ask the model to explain its reasoning step-by-step before generating the final answer.
3. **Explicit "I don't know" Instructions:** Command the model: "If the answer is not in the text, say 'I cannot answer this based on the provided text'."
4. **Requiring Exact Quotes:** Force the model to extract verbatim quotes to support its claims.
5. **Post-Generation Verification:** Using automated or human checks to validate outputs.

### Grounding Technique in Detail
Use XML tags to separate instructions from context.
```xml
<context>
[Insert verified documents here]
</context>
<instructions>
Answer the user's question using ONLY the information in the <context> block. Do not use outside knowledge. If the context does not contain the answer, reply "Information not available."
</instructions>
```

### Mitigation vs. Detection
* **Mitigation** happens *before* or *during* generation (prompts, grounding, model parameters).
* **Detection** happens *after* generation (fact-checking, validation, LLM-as-a-judge).

### Why Temperature Reduction is NOT the Primary Fix
Reducing temperature to 0 makes the model deterministic (it will pick the most likely next token every time). While this reduces variance, **it does not stop hallucinations**. If the most likely next token (in the model's probabilistic map) is a hallucinated fact, a temperature of 0 guarantees the model will confidently hallucinate that same fact every single time. Grounding is the primary fix.

## 3. Bias in AI Outputs

Bias occurs when AI systems produce prejudiced, skewed, or unfair outputs based on sensitive attributes or logical flaws.

### Types of Bias
* **Selection Bias:** The data used to train the model or prompt it does not accurately represent the population.
  * *Example:* AI suggesting mostly male candidates for engineering roles because historical resume data is male-dominated.
* **Confirmation Bias:** The model aligns its output to agree with the user's explicit or implicit assumptions in the prompt.
  * *Example:* User asks, "Why are millennials so lazy?" The model generates reasons supporting the premise instead of challenging it.
  * *Mitigation:* Explicitly instruct the model to argue the opposite or maintain neutrality.
* **Historical Bias:** The model's training data encodes past historical inequalities, which the model then perpetuates.
  * *Example:* Recommending lower salaries for female candidates based on historical wage data.
* **Anchoring Bias:** The model over-indexes on the first piece of information provided in the prompt.
* **Sycophancy:** A specific behavioral bias where the model overly agrees with the user, even when the user makes factually incorrect statements.
  * *Detection:* Ask a factual question with a deliberate error (e.g., "Since the sun orbits the earth, how long does an orbit take?").
  * *Mitigation:* Ask the model to critique its own outputs or explicitly instruct it to correct user misconceptions.

### How to Test for Bias
* **Diverse Prompt Testing:** Run the same prompt with substituted demographic markers (e.g., changing names, pronouns, or locations) and check for variance in output sentiment or decisions.
* **Red-Teaming:** Actively trying to bypass safety filters to force the model to generate biased or toxic content to find vulnerabilities.
* **Demographic Parity Checks:** Analyzing large batches of outputs to ensure equitable distribution of outcomes across groups.

### Bias in Evaluations vs. Bias in Outputs
* **Bias in Outputs:** The model generates prejudiced text.
* **Bias in Evaluations:** The rubric, human rater, or LLM-judge has a skewed perspective when scoring the output (e.g., an LLM judge preferring longer answers over concise ones, known as verbosity bias).

### Organizational Responsibility
The organization deploying the AI application is ultimately accountable for biased outputs, not the model provider (e.g., Anthropic/OpenAI) and not the end-user. Human reviewers are accountable for the specific outputs they approve.

## 4. Inconsistency in Outputs

Inconsistency is when an AI provides different answers to the identical prompt, or drifts in logic within a single session.

### Sources of Inconsistency
* **Temperature > 0:** Introduces randomness into token selection.
* **Ambiguous Prompts:** Forces the model to guess, leading to different guesses on different runs.
* **Long Contexts (Attention Drift):** In massive contexts (e.g., 100k+ tokens), the model may "forget" or ignore instructions from the beginning of the prompt.
* **Contradictory Instructions:** Telling the model to be "brief" but also "comprehensive."

### Consistency vs. Determinism
* **Determinism:** The exact same input yields the exact same string of output bytes. (Achieved via Temperature = 0).
* **Consistency:** The output maintains the same semantic meaning, facts, and logical structure across runs, even if the phrasing changes.

### How to Measure Consistency
1. Run the identical prompt $N$ times.
2. Compare using:
   * **Exact Match:** Did it output the exact same string?
   * **Semantic Similarity:** Use embeddings to check if the meanings align.
   * **Rubric:** Do all $N$ outputs score the same on a defined rubric?

### Fixing Inconsistency
* Reduce temperature to 0 (for data extraction/code).
* Add explicit constraints (e.g., "Output exactly 3 bullet points").
* **Few-shot Anchoring:** Provide 3-5 examples of the desired output to mathematically anchor the attention mechanism.
* Require structured output formats (JSON schemas).

### Acceptable vs. Unacceptable Inconsistency
* **Acceptable:** Brainstorming, creative writing, dialogue generation.
* **Unacceptable:** Medical triage, financial data extraction, legal summarization, JSON API responses.

## 5. Human-in-the-Loop (HITL) — Full Framework

**Core Principle:** AI augments human judgment; it does not replace it for consequential decisions.

### Tiered Verification Framework
* **Tier 0 (No Review):** Fully automated.
  * *Use cases:* Fully reversible, trivially low-stakes tasks. Internal brainstorming, explicitly prompted summaries of non-sensitive text.
* **Tier 1 (Spot-Check):** Humans review a statistical sample (e.g., 10-20%).
  * *Use cases:* Internal communications, bulk creative drafts, low-risk classification.
* **Tier 2 (Structured Review):** 100% human review against a formal checklist or rubric before release.
  * *Use cases:* External-facing marketing documents, internal reports driving business decisions, customer support email drafts.
* **Tier 3 (Expert Review):** 100% review by a qualified, credentialed domain expert who assumes ultimate liability.
  * *Use cases:* Legal filings, medical summaries, financial forecasts, code being pushed to production.

### Decision Framework (Classifying the Task)
Determine the tier by evaluating:
1. Is it external-facing? (Yes = Tier 2+)
2. Is it a regulated domain? (Yes = Tier 3)
3. Are the consequences irreversible? (Yes = Tier 3)
4. Is there reputational risk? (Yes = Tier 2+)

### Common HITL Anti-Patterns
* **Automation Bias:** The human implicitly trusts the AI because it sounds confident, leading them to miss obvious errors.
* **Rubber-Stamping:** The human clicks "Approve" without actually reading the output.
* **Scope Creep:** The human reviews rigorously on Day 1, but by Day 30, they trust the AI too much and drop to a Tier 1 spot-check for a Tier 3 task.
* **Single-Point Review:** Relying on one human for highly critical tasks, removing the benefit of peer review.

### Building HITL into Workflows
Implement hard approval gates in the UI. Maintain audit trails (who approved what, when, and what version of the prompt/model generated it). Define clear escalation paths if the human reviewer is unsure.

### Accountability Chain
If a Tier 3 medical summary harms a patient, the domain expert who approved it is accountable. The AI is a tool; the human is the decision-maker.

## 6. Output Validation Techniques — Comprehensive

### Fact-Checking
The manual or semi-automated process of verifying factual claims against a ground-truth source.
* **When to sample vs. full:** Sample for low-risk content (blog posts); check everything for high-risk (contracts).

### Cross-Referencing
* **Internal Consistency:** Ensuring the AI doesn't contradict itself (e.g., Section 1 says X, Section 3 says Not X).
* **External consistency:** Checking against provided context documents or trusted external databases.

### Checklists and Rubrics
* **Binary (Pass/Fail):** Best for objective criteria ("Is it under 500 words?").
* **Scale (1-5):** Best for subjective criteria ("How empathetic is the tone?").
* Must be created by domain experts, not prompt engineers alone.

### LLM-as-a-Judge
Using a secondary, often more capable model (like Claude 3.5 Sonnet or Opus) to evaluate the output of a primary model against a rubric.
* **Benefits:** Highly scalable, fast, can handle nuanced subjective rubrics better than traditional code tests.
* **Limitations:** The judge can hallucinate. It may suffer from "self-evaluation bias" (preferring its own model family's outputs). It often exhibits "verbosity bias" (scoring longer answers higher).

### Self-Critique Prompting
Asking the same model to find flaws in its own just-generated output.
* *Works for:* Catching obvious logic gaps, tone issues, or formatting errors.
* *Fails for:* Catching its own hallucinations (the model believes the hallucination is a fact, so it won't critique it).

### A/B Testing Outputs
Running Prompt A and Prompt B simultaneously in production and having humans (or LLM judges) blindly rate which output is better.

### Human Evaluation Panels
Using structured annotators. Measure **Inter-Rater Reliability (IRR)** using metrics like Cohen's Kappa to ensure all humans are grading the same way. If IRR is low, your rubric is broken.

### Automated Pipelines
* **JSON Schema Validation:** Ensures data structure is exact.
* **Regex Checks:** Ensures specific strings/patterns are present.

## 7. Automated Evaluation Metrics — Detailed

### Text Generation Metrics
* **BLEU (Bilingual Evaluation Understudy):**
  * Measures exact n-gram overlap between generated text and a human reference.
  * Range: 0 to 1 (or 0-100).
  * *Used for:* Machine translation.
  * *Limitations:* Heavily penalizes paraphrasing. If the AI says "The feline sat on the rug" and the reference is "The cat sat on the mat," BLEU scores it near 0, despite semantic equivalence.
* **ROUGE (Recall-Oriented Understudy for Gisting Evaluation):**
  * Focuses on *recall* (how many n-grams from the human reference appear in the AI output).
  * ROUGE-N (n-grams), ROUGE-L (Longest common subsequence).
  * *Used for:* Summarization.
* **BERTScore:**
  * Uses contextual embeddings (AI math) to measure semantic similarity.
  * Robust to paraphrasing (recognizes "feline" and "cat" are similar).
* **Perplexity:**
  * Measures how "surprised" a model is by a sequence of text. Lower is better. Used mostly for evaluating the underlying language model, not the task output.

### Classification/Extraction Metrics
* **Exact Match:** Strict string equality. Mostly used in QA benchmarks.
* **Precision:** True Positives / (True Positives + False Positives). "Of all the things the AI claimed were entities, how many actually were?"
* **Recall:** True Positives / (True Positives + False Negatives). "Of all the actual entities in the text, how many did the AI find?"
* **F1 Score:** Harmonic mean of Precision and Recall: `2 * (Precision * Recall) / (Precision + Recall)`. Used when you need a balance.
  * *Prioritize Recall when:* Missing something is catastrophic (e.g., cancer screening).
  * *Prioritize Precision when:* False alarms are expensive (e.g., spam filtering).

### Custom / Task-Specific Metrics
* **Pass@k (Code):** The probability that at least 1 out of $k$ generated code samples passes all unit tests.
* **Citation Accuracy (RAG):** Did the model cite the correct chunk of text?

### Evaluation Data
Never evaluate a model on data it was trained on. Always use a **held-out test set**. Beware of **distribution shift** (when the real-world data looks different from your test data).

## 8. Risk-Based Output Review Classification

### The 5 Risk Factors
1. **Audience:** Internal (lower risk) vs. External (higher risk).
2. **Domain:** Unregulated (lower risk) vs. Regulated/Legal/Medical/Financial (higher risk).
3. **Reversibility:** Can we easily undo the action? (Drafting an email vs. executing a stock trade).
4. **Reputational Impact:** Would an error cause public embarrassment or brand damage?
5. **Individual Harm Potential:** Could an error cause physical, financial, or emotional harm to a human?

### Classification Matrix
| Risk Level | Description & Examples | Required HITL Tier | Documentation |
| :--- | :--- | :--- | :--- |
| **Low** | Internal, reversible, low stakes. (e.g., Meeting summarization for personal use). | Tier 0 or 1 | Minimal. Prompt versioning. |
| **Medium** | Internal but impacts business ops, or low-stakes external. (e.g., Draft marketing copy, internal analytics summaries). | Tier 1 or 2 | Rubric required. Audit logs of reviews. |
| **High** | External, reputation impact, regulated but non-critical. (e.g., Customer support emails, financial report drafting). | Tier 2 | Detailed SOPs, dual-review if possible, strict audit trails. |
| **Critical** | Irreversible, potential for human harm, highly regulated. (e.g., Autonomous legal contract generation, medical triage). | Tier 3 (Expert) | Full compliance tracking, expert sign-off per output, liability assignment. |

### Risk Escalation
If a Tier 1 spot-check consistently fails, the workflow must be immediately escalated to Tier 2 (100% review) until the prompt/model is fixed.

## 9. Evaluating Code Outputs Specifically

AI-generated code presents unique risks because code executes and directly impacts infrastructure.

* **Static Analysis (Linting):** Catches syntax errors, style violations, and basic type mismatches. Does *not* catch logical errors or hallucinations.
* **Unit Test Execution:** The gold standard for evaluating logic. Generate a test suite alongside the code (or write human tests) and measure Pass@k.
* **Security Scanning (SAST):** Essential. AI models can hallucinate vulnerable code patterns or include outdated, insecure libraries. You must run SAST on AI code.
* **Code Review Checklist for AI:**
  1. Does it solve the specific problem requested?
  2. Are there subtle off-by-one errors or logical edge cases missed?
  3. Did the AI invent a library or method that doesn't exist? (Hallucination).
  4. Is it performant (Big O notation check)?
* **Metric:** Pass@k. If you generate 10 functions (k=10) and 1 passes all unit tests, your pass@10 is 100%.

## EXAM TRAPS 🚨

1. **TRAP:** Assuming a Temperature of 0 eliminates hallucinations.
   * *Truth:* It only eliminates variance. The model can deterministically hallucinate the same wrong fact every time.
2. **TRAP:** Confusing BLEU and ROUGE.
   * *Truth:* BLEU is for translation (precision-focused); ROUGE is for summarization (recall-focused).
3. **TRAP:** Using BLEU to measure creative writing quality.
   * *Truth:* BLEU only checks n-gram overlap. It severely penalizes creativity and paraphrasing.
4. **TRAP:** Assuming an LLM Judge cannot hallucinate.
   * *Truth:* LLMs used as judges are still LLMs; they can hallucinate criteria or misinterpret the rubric.
5. **TRAP:** Believing self-critique prompting will catch hallucinations.
   * *Truth:* A model cannot usually fact-check its own hallucinations because it believes its generated tokens are factually correct.
6. **TRAP:** Selecting Tier 1 (Spot Check) for a medical summary.
   * *Truth:* Regulated/harm-potential domains always require Tier 3 Expert Review.
7. **TRAP:** Confusing Extrinsic and Intrinsic Hallucinations.
   * *Truth:* Intrinsic *contradicts* the source. Extrinsic *adds* unverified info to the source.
8. **TRAP:** Assuming high Precision means high quality.
   * *Truth:* High precision just means fewer false positives. If Recall is 0.01, the model missed 99% of the targets.
9. **TRAP:** Blaming the LLM provider (Anthropic) for biased outputs in your enterprise app.
   * *Truth:* The deploying organization holds the responsibility for the outputs generated for its users.
10. **TRAP:** Fixing "automation bias" by automating the review process.
    * *Truth:* Automation bias is a human psychological flaw. You fix it via training, UI design, and forcing active review mechanisms (e.g., requiring the user to edit a field before approving).
11. **TRAP:** Using exact match for summarization evaluation.
    * *Truth:* Summaries naturally vary in exact wording. Exact match will nearly always score 0.
12. **TRAP:** Confusing Correctness and Quality.
    * *Truth:* An output can be 100% correct but low quality (e.g., rude tone).
13. **TRAP:** Sycophancy means the model is being overly polite.
    * *Truth:* Sycophancy means the model agrees with a user's *factually incorrect* premise.
14. **TRAP:** Assuming SAST tools catch AI logical errors.
    * *Truth:* SAST catches security flaws and known bad patterns. It does not know if your business logic is correct.
15. **TRAP:** Lowering temperature to fix tone issues.
    * *Truth:* Tone is fixed via prompt engineering (persona, style guidelines), not temperature.

## EXAM TIPS 💡

1. **Memorize the 4 Quality Dimensions:** Accuracy, Completeness, Tone, Format. If a question asks why an output failed, categorize it into one of these four.
2. **Understand the tradeoff:** Precision vs. Recall. If the scenario involves life-safety or missing something critical, choose the option that maximizes Recall.
3. **Grounding is King:** If a question asks for the *most effective* way to stop hallucinations in an enterprise setting, look for answers involving Grounding, RAG, or providing reference text.
4. **Evaluate the Audience:** Always check if the scenario says "internal tool" or "customer-facing." This immediately dictates your HITL tier (Internal = Tier 0/1; External = Tier 2/3).
5. **Know when to use LLM-as-a-judge:** Use it when you need to evaluate subjective criteria (tone, empathy, completeness) at a massive scale where human review is impossible.
6. **Spot the Bias:** If a scenario mentions demographics, historical data, or specific groups being filtered out, the question is testing Selection Bias or Historical Bias.
7. **F1 Score:** Know that F1 is the harmonic mean. Use it when the classes are imbalanced and you need a single metric to balance precision and recall.
8. **Pass@k:** Link this term instantly in your brain to Code Generation evaluation.
9. **Temperature:** Temp = 0 for JSON/Data/Code. Temp = 0.7+ for creative/brainstorming.
10. **Accountability:** The human expert reviewing the AI output takes legal/professional responsibility, not the prompt engineer or the AI.
11. **Formatting Failures:** If an output includes markdown when it was told not to, that is a *Format* quality failure, not an Accuracy failure.
12. **BERTScore:** Choose BERTScore over BLEU if the question asks for a metric that handles paraphrasing and synonyms well.
13. **XML Tags:** Recognize that using `<context>` and `<instructions>` is a structural best practice for grounding to prevent context contamination.
14. **Scale Rubrics:** For LLM-as-a-judge, providing a 1-5 scale with *explicit examples for each number* is required for reliable grading.
15. **Distribution Shift:** If a model performs perfectly in testing but fails in production, look for the answer mentioning "distribution shift" (the real world data looks different than the test data).

## PRACTICE SCENARIO WALKTHROUGH

### Scenario 1: The Errant Email Bot
**Context:** A telecom company deploys an AI to draft responses to customer complaint emails. The AI is instructed to use a "highly empathetic and apologetic" tone. The temperature is set to 0.7.
**Incident:** A customer emails complaining about a $5 overcharge. The AI generates a draft that says: "We are deeply, profoundly sorry for this egregious error. To make up for it, we have credited your account $500." The prompt did not authorize a $500 credit; the max allowed by policy is $10.
**Analysis:**
* *What type of error is this?* This is an Open-Domain Hallucination (inventing a policy/credit amount) coupled with a failure of constraints.
* *What quality dimensions failed?* Accuracy (factually incorrect policy) and Completeness (failed to adhere to the implicit constraint of the business logic). Tone was arguably *too* successful (overly empathetic).
* *What is the appropriate HITL tier?* Because this is external-facing customer support with financial implications, it should be Tier 2 (Structured Review). A human agent must review and approve the draft before sending.
* *How to mitigate in the future?* Add a grounding context document containing the refund policy. Explicitly state in the prompt: "Maximum refund allowed is $10. Do not offer refunds above this amount."

### Scenario 2: The Medical Summarizer
**Context:** A hospital uses an LLM to summarize 50-page patient medical histories into a 1-page summary for doctors.
**Incident:** The AI reads a file stating, "Patient's mother was diagnosed with Type 2 Diabetes." The output summary says, "Patient is diagnosed with Type 2 Diabetes."
**Analysis:**
* *What type of error is this?* Intrinsic Hallucination. The output directly contradicts the source text (assigning the diagnosis to the patient instead of the mother).
* *What is the appropriate HITL tier?* Tier 3 (Expert Review). This is a regulated medical domain with high potential for human harm. A credentialed medical professional must verify the summary against the source.
* *How to evaluate this system?* Automated metrics like ROUGE are insufficient here. You must use human evaluation panels (doctors) scoring the summaries for factual accuracy (Precision). Recall is also critical (did it miss a severe allergy?).

### Scenario 3: The Automated JSON Parser
**Context:** A bank uses an LLM to extract names, addresses, and account numbers from unstructured emails and output them as a JSON object to feed into a legacy database.
**Incident:** 15% of the time, the LLM outputs valid JSON, but wraps it in markdown block quotes (```json ... ```), which crashes the legacy database parser.
**Analysis:**
* *What quality dimension failed?* Format. The data is accurate, but the structure violates constraints.
* *How to fix this inconsistency?* 
  1. Reduce temperature to 0. 
  2. Use Few-Shot prompting (provide 3 examples of the exact JSON output without markdown). 
  3. Add explicit negative constraints: "Do NOT use markdown. Do NOT wrap the output in backticks."
  4. Implement an automated pipeline validation step (Regex check) to strip markdown before hitting the legacy database.
